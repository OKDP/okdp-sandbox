# OKDP deployments layout (bootstrap)

This directory bootstraps the desired state of an OKDP platform: the **sources**
(`platform/`, `projects/`) and the entry points of the engines (`flux/`, `argocd/`).
Every instance is **compiled** into what Helm installs, the same under both engines:
the people and the console write the sources, a compile writes `compiled/`, and the
engines deploy `compiled/`. `scripts/configure.sh --push` compiles the committed layout
and puts the sources and the compiled tree on the sandbox's Forgejo, which holds the
**only desired state** from then on: the console (through the control plane server)
and the people commit the sources there, the **CI** of the sources compiles each push
into the output ([okdp-gitops](https://github.com/OKDP/okdp-gitops), on the Forgejo
Actions runner [`30-forgejo-runner`](platform/components/30-forgejo-runner/values.yaml)),
and Flux **or** Argo CD deploys it. The compiled tree is never in this repository. An instance names a **package** of a service catalog (a Git
repository, [below](#service-catalogs)), which
[okdp-compiler](https://github.com/OKDP/okdp-compiler) compiles into an umbrella chart
over the upstream charts of the service, with its values. Nothing OKDP is pulled from a
chart registry.

On Forgejo, the sources and the compiled tree live in one repository or in several:
the **topology** ([below](#topologies)), chosen with `scripts/configure.sh`.

## Layout

```
platform/
  platform-values.yaml            # {global: {okdp: {...}}}: the platform's context of every instance
  catalog.yaml                    # the service catalogs (repositories) and the console menu
  projects.yaml                   # split topology only: the projects, one repository each
  connections/<name>.yaml         # {connections: {<name>: {...}}}, external connections for components
  components/<NN>-<name>/         # platform components; NN = layer 00, 10, 20 or 30
    instance.yaml  values.yaml    #   written by hand
projects/<project>/
  project.yaml                    # {name, description, ...}; namespace = <project>
  connections/<name>.yaml         # {connections: {<name>: {...}}}  (external connection)
  services/<instance>/
    instance.yaml                 # service and version (a catalog package), connection files
    values.yaml                   # user parameters only
    upstream.<key>.yaml           # optional: upstream values of one chart of the package
compiled/                         # generated by okdp-gitops compile (and the console), in the
                                  # output repository only (not here): never edit
  platform/kustomization.yaml     #   ConfigMap okdp-platform-values (both engines)
  platform/platform-values.yaml   #   its file, a copy of platform/platform-values.yaml
  platform/components/<NN>-<name>/  # the compiled instance, its engine files (Generated files)
  projects/<project>/kustomization.yaml               # Flux: the services of the project
  projects/<project>/services/<instance>/             # the compiled instance, its engine files
flux/                             # Flux entry point (reads the output repository)
  sync.yaml                       #   GitRepository okdp-gitops + Kustomization okdp (bootstrap)
  platform.yaml                   #   Namespace okdp-releases, Kustomization okdp-platform-values
  components.yaml                 #   generated, output repository only: one Kustomization per
                                  #   platform component, okdp-projects
  kustomization.yaml
argocd/                           # Argo CD entry point (reads the output repository)
  project.yaml                    #   AppProject okdp (platform)
  root.yaml                       #   Application okdp (manages argocd/ itself)
  platform-values.yaml            #   Application okdp-platform-values
  components.yaml                 #   Application okdp-components: the components' Applications (waves by layer)
  services.yaml                   #   Application okdp-services: the services' Applications
  projects.yaml                   #   ApplicationSet okdp-projects (one AppProject per project)
  okdp-project/                   #   chart of the AppProject project-<p>
  bootstrap/                      #   patches of the Argo CD configuration (applied once, by hand):
    argocd-cm-patch.yaml          #     the health of Applications, the sign-in with Keycloak
    argocd-rbac-cm-patch.yaml     #     the Argo CD roles of the Keycloak users
optional/                         # components and services not deployed, moved into place by hand
  storage/<store>/                #   the 20-storage stores not in use (scripts/configure.sh)
```

The [scripts](#scripts) that configure, compile, check and push this layout are at the
root of the repository, in `scripts/`.

Names used below: `<p>` project, `<i>` instance, `<r>` = `<p>-<i>` the Helm release
name, `<c>` a connection name, `<NN>` a layer.

## Topologies

Each part of the layout may live in its own repository of the sandbox's Forgejo
(organization `okdp`, `http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/<repository>.git`,
branch `main`):

| Part | Content | `mono` | `io` | `split` |
|---|---|---|---|---|
| platform | `platform-values.yaml`, `catalog.yaml`, `connections/`, `components/`, `projects.yaml` (split) | `okdp-deployments`, `platform/` | `okdp-input`, `platform/` | `okdp-platform`, its root |
| project `<p>` | `project.yaml`, `connections/`, `services/` | `okdp-deployments`, `projects/<p>/` | `okdp-input`, `projects/<p>/` | `okdp-project-<p>`, its root |
| output | `compiled/`, `flux/`, `argocd/` | `okdp-deployments`, its root | `okdp-output`, its root | `okdp-output`, its root |

- `mono` (the default): one deployments repository, `okdp-deployments`, the sources
  and the output side by side at its root. It is not this repository, which only
  bootstraps it.
- **Flux and Argo CD read the output repository only**: `flux/` and `argocd/` name it,
  and their paths are at its root (`./flux`, `./compiled/...`) in every topology.
- The control plane server reads the topology from its values
  ([`30-okdp-control-plane-server`](platform/components/30-okdp-control-plane-server/values.yaml)):
  without `gitops.topology`, `gitops.repoURL` and `branch` are the mono repository
  (the layout at its root, no `gitops.path`); with it, the topology file
  (`GITOPS_CONFIG`) gives each part:

  ```yaml
  topology:
    platform: {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-platform.git, branch: main, path: ""}
    projects: {url: "http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-project-{project}.git", branch: main, path: ""}
    output:   {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-output.git, branch: main, path: ""}
    forgejo:  {url: http://forgejo-http.forgejo.svc.cluster.local:3000, owner: okdp}   # split
  forgejoTokenSecret: okdp-forgejo-token                                               # split
  ```

  `okdp-gitops compile --config <file>` reads the same file (a `url` may also be a
  local directory, read and written in place).
- A change, the console's or a person's, is a commit of the sources (platform or
  project repository); the CI of that repository compiles it into the output
  repository (`okdp: compile`, from the latest sources of every part), which the
  engines deploy. A change that does not compile writes no output (the console
  refuses it before it commits). `okdp-gitops compile --check` fails while the output
  is stale. The CI runner (`30-forgejo-runner`) reads the same topology file, its
  `topology` value (`scripts/configure.sh --topology` writes both).
- `split`: `platform/projects.yaml` lists the projects (`projects: [{name: demo}]`, a
  project may override the `url`, `branch` or `path` of the template). The console
  creates a project's repository `okdp/okdp-project-<p>` through the Forgejo API (the
  token of Secret `okdp-forgejo-token`, mounted at `/etc/okdp/forgejo/token`), pushes
  its `project.yaml` and its CI (`.forgejo/workflows/okdp-gitops.yaml`), and adds it
  to `projects.yaml`.

**This directory holds the sources and the entry points of every topology**, never
the compiled tree: the topology changes where each part is pushed, the URL of `flux/`
and `argocd/`, `gitops.topology` of the server, and `platform/projects.yaml`; the
compile happens at the push. `scripts/configure.sh` does both steps:

```sh
scripts/configure.sh --topology io      # or -i; edits the layout
git add -A gitops && git commit -m "chore: configure the sandbox"
scripts/configure.sh --push             # Forgejo installed (README, step 3)
```

`--topology mono|io|split` writes (io, split) or removes (mono) `gitops.topology` and,
for split, `gitops.forgejoTokenSecret`; points `flux/` and `argocd/` at the output
repository (`okdp-deployments` in mono, `okdp-output` otherwise); writes (split) or
removes `platform/projects.yaml`. `--show` prints the topology and its repositories.

`--push` compiles the committed layout (`HEAD`) into the output tree, as
[`scripts/compile.sh`](#compiling-from-the-sources-to-compiled) does (nothing is
pushed when it does not compile), and puts it on Forgejo, through a `kubectl
port-forward` of the current context (or `FORGEJO_URL`), with the admin account of
[`20-forgejo`](platform/components/20-forgejo/values.yaml): it creates the organization
`okdp` and the repositories (public: the engines and the console read them
anonymously), copies the [service catalogs](#service-catalogs), then pushes:

| | mono | io | split |
|---|---|---|---|
| sources | `platform/`, `projects/` to `okdp-deployments` | `platform/`, `projects/` to `okdp-input` | `platform/` to `okdp-platform`, `projects/<p>/` to `okdp-project-<p>` (each project of `projects.yaml`) |
| output | `compiled/`, `flux/`, `argocd/` next to them, in the same commit | `compiled/`, `flux/`, `argocd/` to `okdp-output` | the same |
| CI | `.forgejo/workflows/okdp-gitops.yaml` (`okdp-gitops workflow`) at the root of each repository of the sources, its Actions enabled; the runner `okdp-gitops` registered for the organization `okdp` (`forgejo forgejo-cli actions register`, the secret of Secret `okdp-forgejo-runner`) | the same | the same |
| token | | | a Forgejo access token of the admin for the server, in Secret `okdp-system/okdp-forgejo-token` (key `token`) |

Each repository gets its part's files as one commit on top of its `main`
(`okdp-sandbox <sha>: <subject>`); `--push` refuses when someone committed there since
(the console, a person; the CI's compiles, `okdp: compile`, excepted: bring their
changes into this repository first), unless `--force`, which replaces them. A push of
the output that loses the race against the CI (which compiles the sources just pushed
to the same tree) is made again on top of it. `--dry-run` compiles, prints what would
be done and keeps the parts it would push. The output pushed this way bootstraps the
sandbox (the runner is one of its components); from then on, the CI compiles each
push of the sources.

## Service catalogs

The packages of the instances come from Git repositories, the catalogs, listed in
[`platform/catalog.yaml`](platform/catalog.yaml):

```yaml
repositories:
  - name: platform-charts         # OKDP/platform-charts: the data services, the control plane
    url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/platform-charts.git
    ref: okdp-compiler            # a branch or a tag
  - name: sandbox-dependencies    # OKDP/sandbox-dependencies: the sandbox's platform services
    url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/sandbox-dependencies.git
    ref: okdp-compiler
```

A catalog holds `catalog/<service>/<version>/` (one package version, immutable once
released: `Chart.yaml`, `okdp.yaml`, `values.cel.yaml`, `config.schema.json`, the
defaults of its charts) and `contracts/<contract>.schema.json`, the contracts of the
connections. A service name is unique across the catalogs; the contracts are the union
of their `contracts/` (one contract in two catalogs is the same file). The console's
menu (`categories`) names the services; a service's versions are its directories at
`ref`, the highest offered unless the entry sets `default`.

`scripts/configure.sh --push` copies each catalog that lives on the sandbox's Forgejo
from its source, at its `ref`. The scripts that compile read the catalogs from the
same sources: `--catalog <name>=<dir|url>` (or `OKDP_CATALOGS="<name>=<src> ..."`), a
directory being read as it is (uncommitted changes included, but `--push` copies its
`ref`); else the checkout `<name>` next to this repository, read at `ref` whatever is
checked out; else `https://github.com/OKDP/<name>.git` at `ref`.

## Files written by people and by the console

### `projects/<p>/services/<i>/instance.yaml`

```yaml
name: trino                     # = <i>, the directory name
project: demo                   # = <p>, the project directory = target namespace
service: trino                  # a package of the catalogs: catalog/<service>/<version>/
version: 480.0.0-1.0.0          # its version (a YAML string)
connections:                    # connection files to layer in, in this order
  - demo-storage
```

A plain chart, with no package (the platform components Forgejo, CloudNativePG and
External Secrets), names its chart instead:

```yaml
name: forgejo
project: forgejo
service: forgejo                                    # the chart's name
chart: oci://code.forgejo.org/forgejo-helm/forgejo  # OCI chart reference, ends with /<service>
version: 17.1.7                                     # exact chart version
connections: []
```

Rules (enforced by the compile, the console's and `okdp-gitops`'s):

| key | rule |
|---|---|
| (all) | keys among `name`, `project`, `service`, `chart`, `version`, `connections`; `name`, `project`, `version` required; a package names its `service`, a plain chart its `chart` (and the sandbox writes `connections` always, `[]` when empty). `name`, `project`, `service`, `chart`, `version` are YAML strings (tag `!!str`: quote a version such as `"6.10.0"` only if needed; `6.10` unquoted is a float and is rejected) |
| `name`, `project`, `service` | DNS label `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$` |
| `name` | equals the directory name; for a component, the directory name without `<NN>-` |
| `project` | equals the project directory (services); free namespace for components |
| `service`, `version` | a package: `catalog/<service>/<version>/` of one catalog |
| `chart` | a plain chart: `^oci://[a-z0-9]([-a-z0-9.]*[a-z0-9])?(:[0-9]+)?(/[a-z0-9]([-a-z0-9._]*[a-z0-9])?)+$`, last path segment = `service` when set; or an `https://` repository, `service` then the chart's name |
| `version` | `^[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z][-0-9A-Za-z.]*)?$` (no ranges, no `+build`) |
| `connections` | a list (use `[]` when empty) of distinct DNS labels; each `projects/<p>/connections/<c>.yaml` exists (for a platform component: `platform/connections/<c>.yaml`) |
| release `<p>-<i>` | at most 53 characters; unique across projects and components |

The objects in `okdp-releases` are named `<p>-<i>` and `values-<p>-<i>`: two pairs that
concatenate to the same name (project `a-b` instance `c` and project `a` instance `b-c`)
collide, and the compile rejects the layout.

### `values.yaml`

Only what the user set (the console writes the submitted parameters): the parameters
of the package (its `config.schema.json`, the console's deployment form). Required;
write `{}` when empty. Never put `global.okdp` or `connections` here. A parameter
naming a connection (`x-okdp-connection-ref` in the schema) holds a connection file
name, the release name of another instance of the project (`demo-hive`, a contract
with a naming convention), or the name of an output another instance of the project
publishes (`demo-pg-hive`, an s3 or database-server output): the instance then waits
for that instance.

### `upstream.<key>.yaml`

Optional, written by hand: values of one upstream chart of the package (its dependency
key), over what the package computes, except the paths the package protects (its
`okdp.yaml`, `upstream.<key>.protect`).

### `projects/<p>/project.yaml`

`{name: <p>, description: ...}`. `name` equals the directory name.

### `projects/<p>/connections/<c>.yaml`

```yaml
connections:
  example-s3:                     # = <c>, the file name without .yaml
    contract: s3                  # a contract of the catalogs: database-server | s3 | hive | iceberg-catalog | trino ...
    apiUrl: https://s3.example.com   # non-secret fields of the contract
    bucket: example
    secretRef:
      name: example-s3-credentials   # Secret in namespace <p> holding the secret fields
```

`check.sh` validates the fields against `contracts/<contract>.schema.json` of the
catalogs (unknown fields, secret fields present, required non-secret fields missing);
the compile checks each connection against the contract the parameter that names it
expects.

### `platform/connections/<c>.yaml`

Same format as a project connection file; used by platform components only (e.g.
`keycloak-db`, the database of `20-keycloak`). Its `secretRef` names a Secret of the
component's target namespace.

### `platform/components/<NN>-<i>/`

Same files as a service instance. `project` is the target namespace and the release is
still `<project>-<name>`; `connections` name files of `platform/connections/`. Layers: `00` CRDs/operators,
`10` infra, `20` identity/storage/db, `30` control plane. A layer starts when every
component of the previous non-empty layer is ready (Flux `dependsOn` + `wait`, Argo CD
sync waves).

## Compiling: from the sources to compiled/

Each instance is compiled into `compiled/<its source directory>/`. A **package**
instance is compiled by [okdp-compiler](https://github.com/OKDP/okdp-compiler) with
its package (`catalog/<service>/<version>/` of its catalog) and the contracts of the
catalogs: its context is the platform's (`platform/platform-values.yaml` and the
connection files of `platform/connections/`), then its project's (`project.yaml`'s
settings under `global`), then its own (the connection files of `connections`, in
their order); its values are its `values.yaml` and its `upstream.<key>.yaml` files (as
`upstream: {<key>: ...}`), under the release `<r>` in the namespace `<p>`. The parameters are checked against the
package's schema, the connections against their contracts, and the result is an
umbrella chart over the package's upstream charts with its values file
`instance.values.yaml` (no chart defaults: Helm applies them), the instance's own
objects, what it publishes and the instances it waits for (okdp-compiler
[docs/01_usage.md](https://github.com/OKDP/okdp-compiler/blob/main/docs/01_usage.md#--output)).
A **plain chart** gets its values layers merged (`platform-values.yaml`, its connection
files, `values.yaml`; later layers win, maps merge deeply, lists are replaced, as with
`helm -f a -f b`) into `values.yaml`.

Who compiles: `okdp-gitops compile` ([okdp-gitops](https://github.com/OKDP/okdp-gitops):
`make build`), always the whole layout, from its sources:
- the CI of the sources, on each push to a repository of the sources: its workflow
  `.forgejo/workflows/okdp-gitops.yaml`, run by the Forgejo Actions runner
  [`30-forgejo-runner`](platform/components/30-forgejo-runner/values.yaml)
  (`okdp-gitops compile --config <its topology> --charts <its chart cache>`), commits
  the output (`okdp: compile`); a push that does not compile writes nothing, and the
  run fails (the **Actions** tab of the repository). The console commits the sources
  only, once their compile passes;
- `scripts/configure.sh --push` runs it on the committed layout and pushes the result
  (the bootstrap);
- `scripts/compile.sh` runs it on the layout as it is, into an output directory, never
  into this one (the output tree is the same in every topology: the output
  repository's content, at its root), with the catalogs read from Git
  ([Service catalogs](#service-catalogs)):

```sh
scripts/compile.sh                          # the layout compiles, or its problems
scripts/compile.sh --output /tmp/okdp-out   # the output tree --push would push
```

It calls `okdp-gitops compile --config <the sources of this directory, the output
directory> --catalog platform-charts=<dir> --catalog sandbox-dependencies=<dir>`. A
clone of the mono deployments repository holds its own output: `compile.sh --root DIR
--output DIR` compiles it in place, for a change committed there by hand. A layout that
does not compile (an invalid `instance.yaml`, a package missing from the catalogs, a
missing connection file, a parameter the package refuses, a reference to an instance
the project does not have) is reported whole, and nothing is written. The values are
checked against each upstream chart's `values.schema.json` by the control plane
server before it commits (its chart cache, `gitops.chartCacheDir`), by the CI (its
`--charts` cache) and by `scripts/check.sh --helm` (Helm renders every compiled instance; `--charts DIR`, a
cache filled by `scripts/pull-charts.sh`, spares it the network).

## Generated files

Written by the compile into the output repository, byte for byte the same whoever
compiles (the format is fixed by the golden files of
[okdp-gitops](https://github.com/OKDP/okdp-gitops), `gitops/testdata/golden`).

| File | Content |
|---|---|
| `compiled/.../<i>/Chart.yaml`, `instance.values.yaml` | a package: the umbrella chart (the package's `Chart.yaml`, its dependencies the upstream charts it renders, the OAuth client charts in `dcr` mode) and its values |
| `.../okdp.objects.yaml`, `templates/okdp.yaml` | a package with objects of its own: the objects, rendered by the umbrella as written |
| `.../okdp.instance.yaml` | a package that publishes something: its URL, usage and the connections it provides (what the console shows of the instance and offers to the others) |
| `.../values.yaml` | a plain chart: the compiled values |
| `.../application.yaml` | Argo CD: Application `argocd/<r>` (release `<r>`, namespace `<p>`), from the output repository `argocd/root.yaml` reads; a package's source the instance's directory with `instance.values.yaml`, a plain chart's its chart and the compiled `values.yaml`; its sync wave after the instances it waits for (and, for a component, its layer `<NN>`) |
| `.../helmrelease.yaml` | Flux: HelmRelease `okdp-releases/<r>` (release `<r>`, namespace `<p>`); a package's chart built from GitRepository `okdp-gitops` at the instance's directory, a plain chart's from an `OCIRepository`; the values from the ConfigMap `values-<r>` alone; `dependsOn` the instances it waits for |
| `.../kustomization.yaml` | Flux: the ConfigMap `values-<r>` of the compiled values file, and `helmrelease.yaml` |
| `compiled/projects/<p>/kustomization.yaml` | Flux: `services/<i>` of every compiled instance of the project |
| `compiled/platform/kustomization.yaml`, `platform-values.yaml` | the ConfigMap `okdp-releases/okdp-platform-values` the control plane server reads (both engines) |
| `flux/components.yaml` | one Flux `Kustomization` per component, path `./compiled/platform/components/<NN>-<i>`, `wait`, depending on the nearest lower non-empty layer (the lowest on `okdp-platform-values`); then `okdp-projects`, path `./compiled/projects`, no `wait` (one broken instance must not block the others), depending on the highest layer |

A failed action never uninstalls the release: an uninstall stops half-way on the objects
the `okdp.io/protected` policies of `00-tools` refuse to delete (CRDs, Deployments), after
their ServiceAccounts are gone. A failed install (`timeout: 15m` per Helm action, for the
slow first installs of a loaded machine) is kept and retried in place every 2 minutes,
without limit (the retry is a Helm upgrade of the failed release), as Argo CD retries a
sync; a failed upgrade is rolled back to the last deployed release, 3 times at most. A
release that never deployed has no rollback target: when the retry of its install fails as
well, the HelmRelease stalls (`MissingRollbackTarget`) until the next change of its files
or `flux reconcile helmrelease --force`.

Without the `dependsOn` of `okdp-projects`, a service installed before the ingress
admission webhook or the CA bundle exists fails its install and its retry, then stalls
(`MissingRollbackTarget`).

### What the server writes, per action

Sources in the platform or project repository, one commit; the CI compiles it into
the output repository (the same repository in mono), the server writes no compiled
file.

| action | sources (the server's commit) | compiled/ (the CI's compile of it) |
|---|---|---|
| deploy instance | `instance.yaml`, `values.yaml` | the instance's directory, the project kustomization |
| edit parameters, upgrade (version), change connections | `values.yaml`, `instance.yaml` | the instance's directory |
| delete instance | removes the instance directory | removes the instance's directory, rewrites the project kustomization |
| create/update connection | `projects/<p>/connections/<c>.yaml` | the files of the instances that layer it in |
| delete connection | removes the file (refused while an instance layers it in) | |
| create project | `project.yaml` (split: the repository `okdp-project-<p>`, then `platform/projects.yaml`) | the project kustomization |
| delete project | removes `projects/<p>/` | removes `compiled/projects/<p>/` |

## Install with Flux

Prerequisites: Flux (tested with v2.9.5: source-controller, kustomize-controller,
helm-controller), the sandbox's Forgejo holding the repositories
(`scripts/configure.sh --push`), and helm-controller started with
`--feature-gates=DisableChartDigestTracking=true`. Without it, helm-controller appends
the OCI digest to the version of a plain chart (`5.2.1+f32d40ce76b5`), so
`.Chart.Version` (the `helm.sh/chart` label) differs from Argo CD's:

```sh
kubectl -n flux-system patch deployment helm-controller --type json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--feature-gates=DisableChartDigestTracking=true"}]'
```

(With `flux bootstrap`, add the same patch to `flux-system/kustomization.yaml`.)

1. `flux/sync.yaml` names the output repository (`scripts/configure.sh --topology`
   sets it). For another Git server, change the URL/branch there and in `argocd/`, and
   `gitops.repoURL` or `gitops.topology` of the server. Commit, push
   (`scripts/configure.sh --push`).
2. `kubectl apply -f gitops/flux/sync.yaml`, from this repository: Flux then reads
   `flux/` from the output repository.

Flux then manages `flux/` itself (Kustomization `okdp`), the platform values
(`okdp-platform-values`, from `compiled/platform`), the components (`okdp-component-*`,
ordered by layer, from `compiled/platform/components`) and all projects
(`okdp-projects`: Flux generates the root kustomization of `compiled/projects/` from the
`compiled/projects/<p>/kustomization.yaml` files). HelmReleases, their sources and
values ConfigMaps live in namespace `okdp-releases`; Helm release storage is in the
target namespace. A package's chart is built from the output repository at every
revision (`reconcileStrategy: Revision`), its upstream charts fetched from their
repositories. Deleting an instance directory uninstalls the release (`prune`): the
compile removes its compiled files.

## Install with Argo CD

Prerequisites: Argo CD (tested with v3.4.2) assessing the health of Applications,
needed by the layer ordering of the platform components (the sync waves of an app of
apps wait for Healthy Applications only then), and, for the sandbox, the sign-in with
Keycloak (client `argocd` of `20-keycloak`, PKCE) and the roles of its users:

```sh
kubectl -n argocd patch configmap argocd-cm --type merge \
  --patch-file gitops/argocd/bootstrap/argocd-cm-patch.yaml
kubectl -n argocd patch configmap argocd-rbac-cm --type merge \
  --patch-file gitops/argocd/bootstrap/argocd-rbac-cm-patch.yaml
# argocd-server reads the OIDC TLS setting at startup only.
kubectl -n argocd rollout restart deployment argocd-server
```

1. The files of `argocd/` name the output repository (`scripts/configure.sh
   --topology` sets it; for another Git server, as for Flux). Commit, push
   (`scripts/configure.sh --push`).
2. `kubectl apply -n argocd -f gitops/argocd/`, from this repository: Application
   `okdp` then reads `argocd/` from the output repository.

Argo CD then manages `argocd/` itself (Application `okdp`), the platform values
(Application `okdp-platform-values`, the same `compiled/platform` kustomization as
Flux), and one Application `<r>` per compiled component and service instance: the
`application.yaml` the compile writes in its directory, applied by the apps of apps
`okdp-components` and `okdp-services` from the output repository. A package's
Application has one source, the output repository at the instance's directory (the
umbrella chart, its dependencies fetched from their repositories),
`helm.valueFiles: [instance.values.yaml]`; a plain chart's has two, the OCI chart
(`repoURL` = chart reference without `oci://` and chart name, `chart` = name,
`targetRevision` = version) and the output repository as `ref: values`, its compiled
`values.yaml`. `releaseName: <r>`; destination namespace `<p>` (`CreateNamespace=true`
for the components). Its sync wave orders it: a component after the lower layers, an
instance after the instances its connections reference (okdp-gitops computes the
waves from the compile of every instance). A service belongs
to the AppProject `project-<p>` (Application `okdp-project-<p>`, chart
`argocd/okdp-project`, one per `compiled/projects/<p>/` directory): sources limited to
the output repository and the registries of its plain charts (`chartRepositories`),
destination limited to namespace `<p>`, no cluster-scoped resource. The same chart
creates namespace `<p>` (the services cannot) and keeps it when the project is removed
(`Delete=false`). `<p>` is the directory name, not the `project` key of
`instance.yaml`, so a file of a project cannot target another namespace; the platform
components keep the AppProject `okdp`. The Applications ignore the `caBundle` that
cert-manager's cainjector, ingress-nginx's certgen hook or trust-manager inject after
the apply (webhook configurations and CRD conversion webhooks,
`RespectIgnoreDifferences=true`); `compare-engines.sh` ignores it too. They sync with
`ServerSideApply=true` and diff server-side
(`argocd.argoproj.io/compare-options: ServerSideDiff=true,IncludeMutationWebhook=true`:
the objects defaulted by the API server or a mutating webhook, such as CloudNativePG
Clusters or trust-manager Bundles, stay in sync) (the CloudNativePG and External Secrets CRDs exceed
the client-side apply annotation limit; Flux's helm-controller applies server-side as
well) and retry without limit (backoff up to 5 minutes): a service may wait for the
platform on a first install. Deleting an instance directory deletes the
Application and its resources (finalizer). The generated `helmrelease.yaml` and
`kustomization.yaml` files are ignored by Argo CD, and `application.yaml` by Flux.

## Scripts

At the root of the repository, in `scripts/`, run from there. They act on this
directory; `configure.sh`, `compile.sh`, `check.sh` and `pull-charts.sh` take another
layout with `--root DIR`.

```
scripts/configure.sh              # engine, 20-storage store, topology; --push: compiled, to Forgejo
scripts/compile.sh                # compiles the layout into an output directory, the catalogs from Git
scripts/check.sh                  # CI: the layout compiles, shapes and contracts valid
scripts/pull-charts.sh            # fills a chart cache with the upstream charts (check.sh --helm)
scripts/compare-engines.sh        # compares the live objects of two clusters (Flux vs Argo)
scripts/e2e-kind.sh               # end-to-end install on a throwaway kind cluster
scripts/lib/                      # shared by the scripts (topology, catalogs, Forgejo)
```

- `scripts/configure.sh [-i] [--engine flux|argocd] [--storage seaweedfs|rustfs]
  [--topology mono|io|split]`: sets `gitops.engine` of the control plane server; swaps
  the `20-storage` component (`instance.yaml`, `values.yaml`) with the one parked in
  `optional/storage/<store>` and rewrites the `internalUrl` of the connection files
  pointing at the store; sets the [topology](#topologies). Without arguments on a
  terminal (or with `-i`) it asks, the current values being the defaults; `--show`
  prints them; the topology is also the CI runner's (`30-forgejo-runner`). Edits the
  layout only. `configure.sh --push [--force] [--dry-run]` then compiles the committed
  layout and puts it, its CI and the catalogs on the sandbox's Forgejo, the CI runner
  registered ([Topologies](#topologies)). Needs yq v4; `--push` also git, okdp-gitops,
  curl, jq and kubectl.
- `scripts/compile.sh [--output DIR] [--catalog NAME=SRC]...`: `okdp-gitops compile`
  of the sources into the output tree DIR (a temporary directory without `--output`),
  the catalogs read from Git; see
  [Compiling](#compiling-from-the-sources-to-compiled). `okdp-gitops` (not a script:
  [okdp-gitops](https://github.com/OKDP/okdp-gitops), `make build`; `OKDP_GITOPS` names
  it).
- `scripts/check.sh [--output DIR] [--catalog NAME=SRC]... [--charts DIR] [--helm]`:
  YAML syntax, file shapes (the catalog's repositories and menu, the instances'
  packages in the catalogs, `flux/` and `argocd/` reading the output repository of the
  topology), connection contracts (from the catalogs' `contracts/`), the layout
  compiles (into a temporary output tree, or `--output DIR`), `kustomize build` of
  every kustomization of that output; `--helm` also runs `helm template` of every
  compiled instance (a package's umbrella, its dependencies from the `--charts` cache
  or `helm dependency build`; a plain chart with its compiled values). Needs yq v4,
  jq, git and okdp-gitops; kustomize and helm optional.
- `scripts/pull-charts.sh --output DIR CACHE`: fills the chart cache CACHE with the
  upstream charts the compiled instances of the output tree DIR (`compile.sh --output
  DIR`) render (the dependencies of the compiled umbrellas, the plain charts), in the
  layout of the compiler's chart cache (`helm pull --untar` under
  `CACHE/<repository>/<chart>-<version>/`), for `check.sh --helm --charts CACHE` (and
  `okdp-compile --check --charts CACHE`). The packages are not pulled: they are read
  from the catalogs. Needs yq v4 and helm.
- `scripts/e2e-kind.sh up|push|down flux|argocd`: installs the layout on a throwaway kind
  cluster, through its Forgejo (`configure.sh --push`, the topology `E2E_TOPOLOGY`), with
  the catalogs of `OKDP_CATALOGS` or next to this repository and the control plane and
  okdp-gitops images of your choice (`E2E_SERVER_IMAGE`, `E2E_GITOPS_IMAGE`); then a
  plain commit of the sources, pushed to Forgejo, must be compiled by the CI and
  deployed. See its header.
- `scripts/compare-engines.sh`: compares the live objects of releases between a Flux
  cluster and an Argo CD cluster, ignoring engine-specific metadata. See its header.
